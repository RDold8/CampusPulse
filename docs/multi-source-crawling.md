# 多站点与轻量采集设计

2026-10-02。当前桌面原型采用Qt Network直接请求网页、Lexbor解析HTML/CSS、SQLite读本地缓存，不启动浏览器、不下载网页图片与CSS、不执行远程JavaScript。此文区分现状与后续设计。

## 学校包是一份来源清单

一个大学包可以维护多个部门、学院和校级站点；每个栏目拥有独立入口、域名允许列表、列表/日期/正文选择器和样本。桌面把这些来源汇总展示，用户按主题、来源和年份筛选，不必知道通知散在哪个部门。

东电当前启用校本部通知、教务通知、考试重修、学工通知、团委通知、团学动态共六个栏目。学工首页以竞赛为主，奖学金公示在第二页，因此增加通用的extraction.pagination字段：next_selector和max_pages。当前学工设置两页；上限允许1至10页，防止分页循环，下一页必须属于允许域，重复通知按学校与URL的稳定ID去重。错误保留已入库信息并计为来源失败，不声称完全覆盖历史。

就业网栏目已发现，但动态列表未启用。页面JavaScript使用/module/getcareers接口；直接请求返回HTTP 400，尚未解决响应契约，因此不能把它当成已接入的招聘数据。没有伪造招聘条目。

## 后续发现与维护流程

1. 社区从学校官方首页的组织机构、部门导航和已知官方子站添加候选来源；不无限递归整个域名。
2. 记录候选入口、部门、主题、公开访问状态及可能的HTML/API适配器。
3. 用真实列表和详情样本验证标题、日期、链接、正文；栏目名不是正确性的充分证据。
4. 验证后启用来源；运行记录最近成功时间、错误、采集量和结构变化。自动发现只提交候选，不能直接扩大允许域或自动执行包内代码。
5. 新学校尽量只写配置；确有新响应格式时贡献共享适配器和样本回归。

未来UI将区分已连接、待核实、暂时失败、停止维护；当前仅有来源筛选、整体覆盖说明和本轮错误消息，尚无完整来源健康面板。

## 采集策略顺序

优先读取学校页面实际使用、无需登录的公开JSON接口；无接口时直接获取HTML并做CSS解析；只有无法得到公开文本且确有必要时才考虑浏览器适配器。当前只实现静态HTML适配器，尚未实现通用JSON适配器或浏览器适配器。

借鉴Scrapy的请求队列、去重、缓存、按域限速和自适应节流思路，保持应用层和数据模型与抓取工具独立。当前使用C/C++可调用的Lexbor，避免另造HTML解析器；Qt Network已承担HTTP，不再重复引入另一套网络栈。

当前具备异步请求、复用网络管理器、本地列表缓存、正文按需读取、已缓存正文直接显示、幂等入库、全局3秒请求间隔和响应大小限制。尚未实现ETag/Last-Modified条件请求、按域并发、增量停止规则、失败退避和性能基准。配置里的未来能力字段不能作为已实现证据。

后续提高速度优先减少无效工作：只更新订阅来源与最近页；对支持的站点发送条件请求；跨不同主机有限并发、同一主机限速；仅新通知或变化通知重新解析详情。先记录请求耗时、字节数、新增通知数和缓存命中率再比较性能，不能用“C++”或“不渲染”替代测速证据。

## 年份与办理时间

年份依据官方发布日期，默认打开当前年份；日期不明进入单独分组，标题里的2026—2027学年不决定归档年份。旧通知保留，不代表办理窗口仍开放；奖学金结果公示不等于奖学金申请。办理阶段、截止证据与提醒是后续模块的独立工作。
