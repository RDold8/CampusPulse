# CampusPulse 分步实施计划

日期：2026-10-02。状态：第1、2、3步完成，第4步待实施。本文件是这轮实施的进度入口；参考调研保存在open-source-references.md，更完整的双端模型是后续设计背景。

## 已确认范围与现状

按顺序实现：1.来源管理与状态，2.保存订阅，3.个人待办及用户确认日期，4.软件内日历与ICS文件导出。用户已选择“软件内日历 + ICS文件导出，手机可导入”。每阶段形成可独立运行的程序、相关行为检查和验收记录，前一步验收后再推进后一步。

这轮开始时基线为C++20、Qt Widgets/Network/SQL、Lexbor、SQLite；六个东电栏目、95条缓存、按年份/来源/主题/关键词筛选、正文及修订记录。“重修 / 缴费”已合并到主题下拉框。初始数据库为版本1；第1步升级至版本2，第2步升级至版本3，加入来源记录、本地订阅、多来源关系、主题标签和阶段提示。

这轮沿用本地桌面方式。手机通过导出的日历文件先得到时间信息；账号、移动App、线上日历订阅、ntfy推送、无人值守采集和AI自动截止识别另排后续阶段。期间可以继续扩展学校包，但不以新增全部高校或解决全部动态站点作为这四步的验收条件。

## 实施与代码边界

MainWindow逐步作为页面组装入口；每阶段只加入已完成页面。使用Qt Widgets页面：通知、来源、订阅、待办、日历。把现有通知列表/详情提取为NoticePage，新增SourcePage、SubscriptionPage、TaskPage和CalendarPage，保持现有筛选与实网验证入口。

domain存纯C++数据，application承担规则与用例，storage实现持久化，adapters处理网络与ICS，desktop负责输入和展示。UI不直接写SQL，爬虫不修改个人完成状态；先建立有实际用途的类，不预铺空接口或工厂。

增量迁移采用SqliteMigrations统一管理，必要的Qt数据库连接封装为storage内部Database。每次升级使用事务，最后更新user_version；旧通知ID、正文和修订保留。阶段验收使用现有v1数据库副本验证升级和反复启动，避免用新建空库代替升级检查。

## 第1步：来源管理与状态

交付页面显示学校包全部来源：名称、官方入口、设计主题、分页上限、接入情况、本地是否暂停、最后尝试/完整成功时间、最近公告日期和错误原因。六个可运行来源与尚未接入的就业网均可见。

具体顺序：

1. SchoolPackage区分完整来源目录与可执行配置；未接入项只展示，不进入队列。本地暂停偏好存数据库，不修改社区学校配置；全部暂停时软件仍能读取缓存。
2. 建立增量迁移，增加source_preferences、source_state及精简fetch_run。来源键使用school_id + source_id，避免不同大学相同栏目键冲突。
3. RefreshCoordinator按来源记录一次运行及已完成页数，增加单来源更新用例。状态区分从未更新、更新中、成功、部分成功、失败、本地暂停和未接入。
4. 第一页成功但第二页失败显示部分成功，保留已经写入与历史缓存；完整成功时间只在全部配置页成功后更新。旧缓存没有抓取时间，初次迁移不伪造最后成功时间。
5. 建立SourcePage，显示状态、更新该来源、暂停/恢复；上次运行中断在重启后显示未完成，不永久留在更新中。

最小持久字段：source_state包含学校/来源键、last_attempt_at、last_full_success_at、latest_published_date、状态、页数、列出条数、错误摘要；fetch_run另保存run_id、开始/结束时间和结果。

验收：v1数据升级后现有缓存与正文历史一致；单来源更新只请求所选来源；断网/解析失效/第二页失败均可见且缓存保留；全暂停重启可读；未接入就业网不会被误认为已连接。

用户追加范围：增加“大学”页面，输入官网首页后通过已安装社区学校包的官方主机精确匹配并加载配置；匹配阶段不联网，不接受任意网址。当前已核验目录为东北电力大学；未收录高校由社区补充学校包。来源和通知按学校隔离，加载学校后保存选择。输入、允许主机与重定向均有约束；详见[第1步验收记录](stage1-validation.md)。

主要改动：SchoolPackage、RefreshCoordinator、SqliteRepository迁移入口；新增domain/SourceState、application/SourceService、storage/SqliteSourceRepository、desktop/SourcePage。

## 第2步：保存订阅与共用匹配规则

交付“我的订阅”：创建、编辑、暂停、删除订阅，把当前筛选保存为订阅并查看命中通知，重启后恢复。

具体顺序：

1. 定义稳定主题键及显示名称，将retake_payment映射为“重修 / 缴费”，保留当前标题含重修的匹配范围；全部主题表示不限制。NoticeFilter与SubscriptionService调用同一NoticeMatcher，不把中文下拉框文字当数据库主键。
2. 订阅保存名称、school_id、来源键集合、主题键集合、阶段键集合、关键词和年份策略。第一版不同维度之间AND，同一来源/主题/阶段集合内部OR；关键词保存包含全部、包含任一与排除项，排除优先。
3. year_policy使用current_year/all_years/fixed_year/unknown_date，fixed_year另保存数字；current_year每次按当前年求值，避免把2026写死。默认沿用今年。
4. 增加subscription表与必要字段验证；现有复杂订阅JSON是未来契约草案，不当成已实现能力。首版通过界面保存本地规则。
5. 增加精简source_occurrence关系，回填旧主来源；相同学校/URL的通知保持一个ID，但记录其出现在多个来源中，来源订阅匹配使用这些关系。
6. 增加轻量多标签和阶段规则；标签键独立于中文名称。列表按标题分别显示重修、补考、缴费，多词用` / `连接；稳定主题分组供筛选和订阅使用，已有缓存立即应用显示规则。申请、报名、缴费、安排、结果、公示分别表示阶段；不明确时显示待核实。订阅命中只产生关注列表，不自动创建个人任务。

验收：重启恢复同一订阅；订阅和相同界面条件得到相同结果；来年current_year跟随年份而fixed_year保持原值；排除关键词有效；同一通知跨栏目出现时各相关来源订阅都能命中；奖学金公示不变成申请任务。

主要新增：domain/Subscription与Theme、application/NoticeMatcher/SubscriptionService/NoticeClassifier、storage/SqliteSubscriptionRepository、desktop/SubscriptionPage；NoticeFilter负责调用共用规则。

第2步已交付保存当前筛选、新建与编辑器、命中预览、暂停/恢复、删除、跳转通知详情和重启恢复。规则与字段详见[本地订阅规则与数据](subscriptions.md)，升级、界面、实网及程序包证据见[第2步验收记录](stage2-validation.md)。

## 第3步：个人待办与确认日期

交付详情页“加入我的待办”和“我的待办”页面。用户填写要完成的操作、个人备注、时间及提醒偏好；先手动确认，后续才增加自动候选日期。

具体顺序：

1. 创建PersonalTask和TaskService，增加personal_task表。字段包括稳定UUID、notice_id、参考修订、标题、操作类型、状态、时间精度、时间值、时区、原文时间说明、确认来源、确认时刻、创建/更新时间及revision。
2. 状态采用未开始、进行中、已完成、已取消；逾期从时间计算，不覆盖实际保存状态。完成是用户自报，已读不会自动完成，程序不核验学校是否收到付款。
3. 时间分为未知、仅日期、明确日期时间。仅日期存纯日期，明确时间保存UTC并保留学校时区。个人设置的时间与摘自原文的时间分别标记；发布日期不会作为截止日期。
4. 同一通知可建立多个任务，例如报名、缴费、核对名单；优先按需手动建立，完整自动流程和跨通知智能合并后置。没有日期的任务仍可保存，但不进入有时间的日历与自动提醒。
5. 支持编辑、完成、撤销完成及取消，保存状态与时间。标题或时间修改保持UUID，重要变更递增revision；保存一次未变化内容不产生新修订。
6. 增加“刷新原文”，已有正文版本改变时提示用户复核关联任务，保留用户已确认的期限和完成状态。周期复查和自动重排另排后续，避免悄悄覆盖个人计划。
7. 任务预留日历稳定UID和提醒偏好；本地提醒实际调度在第4步随日历落地。

验收：从通知创建任务后重启仍可查看；同通知不同操作分开完成；无日期可以保存；未知日期/公示区间不会自动生成申请截止；修改时间仍是同一任务；原文更新提示复核。

主要新增：domain/PersonalTask/TaskTime、application/TaskService、storage/SqliteTaskRepository、desktop/TaskPage/TaskEditorDialog。

第3步已交付上述功能、数据库版本4及可运行程序包。日期、状态、原文复核与存储契约见[个人待办与确认时间](tasks.md)；测试、真实旧库升级、Qt操作和实际桌面窗口见[第3步验收记录](stage3-validation.md)。日历UID和提醒偏好已保存，实际日历与提醒投递仍属于第4步。

## 第4步：内置日历、ICS导出与最小本地提醒

交付月历、选中日期的任务列表、“今天”入口、未完成/历史显示选项，以及导出选中任务或选中月份的ICS文件。日历读取PersonalTask中的已确认时间，不复制一套可独立漂移的截止字段。

具体顺序：

1. CalendarService把已确认时间的任务投影成CalendarItem；未知时间留在待办的日期待定区域。月份/天按学校时区显示，完成与取消状态可区分。
2. CalendarPage采用Qt月历与日期列表；选中条目打开同一任务编辑器，保存后待办和日历同时更新。第一版先实现月视图与日列表。
3. CalendarExporter采用libical C接口封装；在该阶段开始先完成Windows/CMake构建与依赖许可验证，锁定版本和校验值。仅适配器链接库，业务和界面不直接调用libical。
4. 仅日期导出全天事件，单日DTEND为次日；明确时间使用UTC输出。截止时刻不虚构时长或23:59。导出保留原文URL、时间说明和用户确认来源；未确认/未知日期不导出。
5. UID由任务UUID稳定派生，修改日期/标题/导出相关状态保持UID并更新SEQUENCE；重复导出不递增版本。文件正确处理中文、换行、转义与折行，写入失败不给出成功提示。
6. 增加本地ReminderScheduler和投递记录，使用每任务明确启用的提醒设置；仅日期任务的提醒时刻由用户设置，与截止日期精度分开。完成/取消后撤销未触发提醒，重启去重，已过期触发不集中补发。
7. 实际查看一次Windows提醒；导出可选VALARM。手机端分别验证导入、全天/准确时间、中文与闹钟；稳定UID不代表所有手机会把重复文件导入当更新。

标准依据：[RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html)；库依据：[libical官方仓库](https://github.com/libical/libical)。文件导入不等于在线订阅，电脑标记完成也不会自动修改已经导入手机的日历；首版界面明确这些使用边界。

验收：待办改日期后本地日历同步；未确认日期不出现；纯日期与准确时间导出正确；重复导出UID稳定、修改递增版本；完成停止后续本地提醒；重启不重复催办。源码和文件格式验证与真实手机导入/提醒分开记录，后者必须在目标日历应用实测。

主要新增：application/CalendarService/ReminderService、adapters/LibicalExporter/DesktopNotificationChannel、desktop/CalendarPage；storage增加提醒偏好与投递记录。任务时间依旧是一处事实源。

## 每一步的推进方式

顺序执行每步内部小项；先领域和迁移、再服务逻辑、最后页面。功能具备后运行相关行为检查及现有回归，打包并查看真实窗口，再记录结果和剩余问题。只有新的修改/失败/疑点才扩大测试。

阶段交付包含可运行程序、实际变化、验收证据与源码阅读入口；用户反馈优先调整当前阶段。第1、2、3步已形成可运行程序包及验收证据，第4步软件功能已经交付，目标手机导入及Windows系统横幅仍需分别实测。
