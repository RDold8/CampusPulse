# CampusPulse 参考项目与下一阶段实施顺序

核查日期：2026-10-02。本文是基于官方仓库、源码和文档的设计建议；本轮没有安装这些项目，也没有把它们接入桌面依赖。当前界面已将“重修 / 缴费”合并到主题下拉框，去掉独立按钮，并保留年份/来源/搜索组合筛选。UI验证见evidence/theme-ui-proof.json和截图。

## 值得参考的四个项目

| 项目 | 适合借鉴的部分 | 在CampusPulse中的位置 |
|---|---|---|
| [RSSHub](https://github.com/DIYgod/RSSHub) | 高校来源按学校/部门组织、维护者、路由样例、共享解析和详情缓存 | 学校包与来源适配器、社区贡献材料 |
| [changedetection.io](https://github.com/dgtlmoon/changedetection.io) | 非浏览器HTTP与浏览器采集分离、只比较有效正文、忽略噪声、变化记录 | 来源刷新、通知修订及变更说明 |
| [libical](https://github.com/libical/libical) | C接口实现iCalendar数据编解码与时区处理 | 未来独立CalendarExporter，不承担爬虫或手机同步 |
| [ntfy](https://github.com/binwiederhier/ntfy) | HTTP发布/订阅消息与现有手机客户端 | 未来可替换NotificationChannel，用于手机提醒试验 |

RSSHub的[广西民族大学人工智能学院路由](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/gxmzu/ai.ts)明确不需要Puppeteer，直接请求HTML并用选择器提取；这是一个具体高校栏目范例，不代表所有高校无需适配。[共享解析源码](https://github.com/DIYgod/RSSHub/blob/master/lib/routes/gxmzu/utils/index.ts)可用于研究日期、相对链接和按URL缓存详情的处理。

changedetection.io的[官方说明](https://github.com/dgtlmoon/changedetection.io#readme)支持普通HTTP和浏览器两种采集方式、内容区域筛选和变化对比。对CampusPulse最有用的情形是原链接未变，正文的截止时间被修改。当前已有正文版本存储，但正文主要在首次查看时获取；还没有持续复查、更正识别及关联提醒更新。

libical提供C API，适合当前C/C++学习路线。先从用户确认的事件导出ICS，再考虑订阅地址；文件导入和持续订阅是不同交付。[iCalendar标准](https://www.rfc-editor.org/rfc/rfc5545.html)规定事件身份和修订字段；持续输出需保留UID并正确更新版本，而不是每次生成新事件。

ntfy的[HTTP发布接口](https://docs.ntfy.sh/publish/)和[手机订阅文档](https://docs.ntfy.sh/subscribe/phone/)可用于先验证手机通知，不必先开发完整移动App。学校采集、订阅匹配、办理截止和用户完成状态仍由CampusPulse负责。当前桌面关闭后采集停止；持续提醒需要未来常驻采集器，或由手机日历负责已知事件的本地提醒。

当前主要研究机制并独立实现。RSSHub仓库采用[AGPL-3.0](https://github.com/DIYgod/RSSHub/blob/master/LICENSE)，直接复制代码不能简单改标为本项目MIT；实际复用代码和分发依赖时保留对应许可。

## 完善顺序

### 第一阶段：来源可信、筛选可保存

增加source_state与fetch_run：来源入口、主题范围、采集页数、最后检查时间、最后成功时间、最新列表发布日期、错误和本轮数量。学校包和运行状态分别存储。最近没有新内容和来源失败必须区分；来源失败不删除缓存。

保存本地订阅规则，包括学校、来源、主题、关键词和年份偏好。“关注重修 / 缴费”不再只是一轮界面筛选。默认年份仍可跟随当前年；用户固定的历史年份不应每次刷新被重置。

标题关键词分类逐步改为多标签，通知阶段独立记录：申请、报名、缴费、安排、结果、公示。奖学金结果公示不能被解释为申请开放。

验收：重新打开软件订阅仍在；单个来源失败可见原因和旧数据时间；奖学金公示不会显示成报名申请。

### 第二阶段：增量采集与内容修订

拆分列表发现与详情刷新，增加请求缓存、条件请求、正文语义哈希与提取器版本。已读通知需要可配置的复查窗口。不同主机有限并发，同一主机限速与退避；记录耗时、传输字节数和缓存命中率再评估提速。

同一URL在多个栏目出现时保留来源出现记录；跨站相同标题只标记疑似转载，不自动丢弃，因为学院截止可能不同。正文延期、修改或撤销必须有依据，不能仅凭页面暂时404取消事项。

验收：重复更新不重复入库；正文修改能展示前后差异；页脚和访问量变化不会触发办理提醒；原通知和更正通知能关联。

### 第三阶段：手动确认的办理事项与日历

先提供“加入我的待办”，由用户确认操作、日期、时区和提前提醒；之后再增加规则提取的候选日期。保留原文依据与日期精度，缺少年份、多个截止和院系上报期限进入待核实。

一条重修通知可以关联报名、缴费、核对名单、上课/考试多个步骤；每一步独立完成，完成缴费不等于办理全部完成。Event与PersonalTask独立于Notice，已过期历史记录默认不生成当前提醒。

新增CalendarExporter和本地提醒通道；ICS使用稳定UID，重要变化增加SEQUENCE。先验证文件导入，再验证订阅更新和取消行为，不把文件导出称为双端同步。

验收：从通知到用户确认事项、待办、导出ICS形成可用流程；未确认日期不能自动提醒；完成事项可停止相应提醒。

### 第四阶段：社区学校包与手机扩展

学校包贡献提供官方入口、部门/学院归属、来源维护者、列表/详情/日期/分页样本和验证命令。CI先检查配置和离线解析；低频实网检查提供来源状态。先接第二所不同布局的大学验证核心通用性。

未来从现有应用层抽出可无界面运行的采集器，与桌面共用适配器和数据模型；再添加认证API、手机同步和通知通道。ntfy可作为手机投递试验；自有移动App用于个人状态与日历管理。消息发送成功、设备接收和用户已读分别记录。

验收：新增普通学校主要修改学校包；特例增加共享适配器，不在核心按学校名称分支；桌面关闭后的采集和提醒有明确运行机制。

## 建议先做的三个具体任务

1. 来源状态面板及fetch_run/source_state持久化，支持失败原因和数据时效。
2. 本地订阅与通知阶段、多标签，能保存“重修 / 缴费”等关注规则。
3. “加入待办”与用户确认日期，随后接ICS导出。

其余阶段按实际样本推进，不一次铺满后台、云账号和多端框架。原有架构与数据模型文档中更完整的实体仍是设计目标，当前SQLite仅实现通知和修订。
